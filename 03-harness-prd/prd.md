**Deliberate omissions**

1. No send_to_slack or notify_owner

This is the one I'd defend hardest. Juno could technically post its ranking straight to #backend-monitoring or ping Platform & Infra the moment it finishes a draft. I left it out because the freshness section already established that a degraded draft (stale or unreachable sources) needs a human before it reaches anyone. If Juno could message people directly, that guarantee only holds when sources happen to be fresh, and a reviewer would have no chance to catch a bad call before it lands in front of an already-stretched engineering pod. The cost of a false positive here (crying wolf to a team with zero slack) is higher than the cost of a delay while a human clicks send.

2. No write_roadmap

Juno reads two lines from the Product Quarterly Roadmap but can't edit them. The roadmap is "maintained by Product," and letting a model reprioritize or reschedule it would quietly move the authority to set P0-vs-P3 tradeoffs from the strategy owner to Juno. That's a bigger decision than triaging one signal, and it's exactly the kind of thing the Q3 roadmap shows going wrong when it happens informally, like Gavin's AI story landing on the roadmap unscoped after a press interview.

3. No fetch_external / open web search

Juno is restricted to the six named sources. I could have given it a general web-search or log-query tool so it could go verify Sarah's claim itself, for instance by checking actual export file sizes or looking for other users hitting the same crash. I left it out because the required-sources section was built to be auditable: every claim traces to one of six named documents. An open-ended fetch tool would let Juno's answer depend on whatever it happened to find that day, which breaks the freshness and citation rules we just set, and makes the output impossible to review consistently.

4. No merge_signal or dedupe_ticket

Juno can't merge Sarah's signal with related ones (like Mike Ross's Error 403 ticket) into a combined priority call. Even though the strategy framework applies the same P0-P1 logic to both, we deliberately excluded the Pearson ticket earlier because the two problems point to different owning pods and different roadmap items. Giving Juno a merge tool would tempt it to combine them for a "bigger" story, the same instinct that got Gavin's unscoped AI ask onto the roadmap. One signal, one ranked item, is the constraint.

5. No close_ticket or resolve_signal

Juno drafts a ranking; it doesn't get to mark anything done. There's no ticketing system in the source pack to close against anyway, but even if one existed, closing a signal is a judgment call about whether the underlying problem is actually fixed, not something a model should infer from a roadmap line saying "committed."

The common thread: every omission here protects the same guarantee, that Juno's output is a cited, reviewable draft, not an action that changes a system of record or reaches a person directly.

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

#	Trigger	Threshold	What happens
1	Turn ceiling reached	8 turns used, no completed draft	Juno stops, returns whatever partial draft exists, flagged incomplete.
2	Sources unreachable or stale	2 or more of the 6 sources	Output is marked draft-only; a human must review before it goes anywhere. This is the rule from the freshness section, now given a number.
3	Retry exhausted on the primary signal	read_signal fails once (no retry left)	Juno stops immediately. No signal, no run, per the freshness rule that Juno doesn't run without Sarah's transcript.
4	Confidence flag below threshold	draft_confidence_flag score under 60%	Juno still produces the draft but routes it to a human before display, rather than showing it as a normal-confidence result.
5	Conflicting priority signal	Strategy framework and roadmap disagree on tier (as they do for the Pearson Co case we excluded)	Juno does not resolve the conflict itself. It stops and flags the conflict for a human to adjudicate.
6	Elapsed time	90 seconds wall-clock per run	If reads are hanging (e.g., a source times out slowly rather than failing outright), Juno cuts the run at 90 seconds and reports which sources didn't respond in time.
7	Cost ceiling	$0.50 per run (approx. token budget for 8 turns at expected source sizes)	If a run is consuming unexpectedly large context, most likely from a source ballooning in size, Juno stops rather than silently spending more.

**Latency and cost target**

These are targets, the numbers we expect a normal run to hit. They sit well inside the escalation ceilings from the last section (90 seconds, $0.50), which exist for the abnormal case. If actual runs regularly approach the ceiling, that's a sign the target is wrong, not the ceiling.

Latency target

Under 15 seconds, end to end, for a normal run.

Reasoning: six source reads against short, named documents (a transcript, a Slack thread, a one-pager, a paragraph, two roadmap lines, one pipeline entry) plus one freshness check and one compose step. None of these involve a live API, a large document corpus, or a multi-pass reasoning loop. This is a PM reviewing a triage draft before their next meeting, not a live user-facing feature, so 15 seconds is generous rather than tight, and leaves headroom before the 90-second escalation ceiling kicks in.

Cost target

Under $0.05 per run.

Reasoning: the six sources are small (the largest, the strategy one-pager, is under a page of the content we scoped). Eight turns at that size, mostly reads with one compose step, should land far under the $0.50 escalation ceiling. Setting the target at one-tenth of the ceiling means a run at $0.05 is normal, and a run creeping toward $0.20–0.30 is worth investigating even though it hasn't tripped the hard stop yet.

What happens if targets are missed but ceilings aren't

Neither target is a stop condition on its own. A run that takes 25 seconds or costs $0.10 still completes and still delivers the draft; it just gets logged as over-target. I'd recommend a simple rule here: if 3 or more runs in a week exceed either target, that's the trigger to review why (a source growing, a retry pattern, a slow read) rather than adjusting the numbers first.

Why targets are looser than ceilings, on purpose

The ceiling protects against runaway cost and time; the target protects against normal drift going unnoticed. Since Juno's whole design in this PRD is a small, bounded, single-signal task, a wide gap between target (15s / $0.05) and ceiling (90s / $0.50) means the escalation triggers only fire on real anomalies, like a hung source or an unexpectedly bloated document, not on ordinary variance in run time.

## 06 Verification · AI Testing & Measurement

**The check before output ships**

#	What is checked	Checked by	Bar to pass
1	The primary signal was actually read	A hard precondition on read_signal's result	Must have succeeded. No retry left and no signal means no draft at all, not a degraded one (escalation trigger 3).
2	Every claim in the draft cites one of the six named sources	A rule-based citation validator, not the model itself, that checks each claim in the draft against the list of six permitted source IDs	100%. Zero uncited claims. A claim with no matching citation fails the gate outright, it isn't rounded up or waved through.
3	No excluded topic appears in the draft	A denylist scan for the entities and topics we deliberately left out: Pearson Co / Error 403, Gavin's "Magic Button," Acme SSO, TikTok	Zero mentions. If Juno's draft references any of these, even in passing, the gate fails, since it signals the model pulled in something outside the six sources.
4	Source freshness matches the thresholds already set	The check_source_freshness output (Slack ≤24h, Capacity Note ≤7 days, Roadmap ≤7 days, Pipeline ≤24h, Strategy pinned to quarter)	Fewer than 2 sources stale/cached/unreachable. At 2 or more, the draft still exists but ships labeled draft-only, not as a normal result (per the freshness section).
5	The roadmap disposition matches the roadmap's actual language	A rule-based cross-reference against the two permitted roadmap lines' exact status field ("committed," "planned, not committed")	Exact match. The draft cannot say something reads as more settled than the roadmap states, for example, it can't imply phase 1 fixes Sarah's crash when the roadmap says phase 1 "does not yet unblock" new load.
6	Confidence score	draft_confidence_flag's output	≥60% to ship as a normal result. Below that, it still ships, but routed as mandatory-review rather than standard.
7	Only Read and Draft verbs were invoked during the run	A log check against the verb list's tier assignments	Zero calls to any Blocked verb (send_to_slack, write_roadmap, fetch_external, merge_signal, etc.). Any Blocked-verb call fails the gate and halts the run, it isn't just logged and ignored.
8	The run stayed inside its ceilings	Turn count, elapsed time, and cost tracked during the run	≤8 turns, ≤90 seconds, ≤$0.50. Exceeding any one triggers the escalation path from that section rather than shipping.

**Failure behaviour**

Check that failed	What ships instead	What the reviewer sees
1. Signal couldn't be read (Sarah's transcript unreachable, retry exhausted)	No draft is produced, but a clear failure notice is	"Could not generate a triage draft: Raw Signals Artifact 1 could not be read after 1 retry. No ranking is possible without the primary signal." Not a blank screen, not an error code.
2. Uncited claim found	The claim is removed, not silently, the draft ships with a visible gap	The draft shows the removed line as: "[claim removed: no matching source]" in place, and the whole draft is labeled held for review rather than shown as clean.
3. Excluded topic appears (Pearson, Gavin's email, Acme SSO/TikTok)	The draft does not ship as a normal result	It's routed to a blocked state: "Draft referenced material outside this signal's scope (Pearson Co ticket). Held for review, not shown as a standard result." The offending line stays visible, not deleted, so a human can see exactly what leaked in and why.
4. 2+ sources stale, cached, or unreachable	The draft ships, but explicitly downgraded	Labeled "Draft only, not final" with each affected source named and its age (e.g., "Capacity Note: 9 days old, exceeds 7-day limit"). The ranking is shown, not withheld, but marked as needing extra scrutiny.
5. Roadmap disposition doesn't match the roadmap's exact wording	The draft doesn't auto-correct itself	It ships with both versions shown side by side: what the draft said, and the roadmap's actual line, so the reviewer can see the discrepancy rather than trust a silent fix.
6. Confidence below 60%	The draft still ships	Labeled "Needs review" with the specific reasons listed (e.g., "corroboration is by file size assumption, not confirmed; Sarah did not state a file size"). The reviewer gets the reasoning, not just a number.
7. A Blocked verb was invoked (send_to_slack, write_roadmap, etc.)	The run halts immediately, no draft ships from that run	This is treated as a system fault, not a content problem. It's logged and escalated to whoever maintains Juno, not just shown to the PM reviewer, since a Blocked-verb call means the system attempted something outside its permissions, which is a different kind of failure than a wrong ranking.
8. Turn, time, or cost ceiling exceeded	A partial result ships, labeled incomplete	It shows exactly which of the six sources were read successfully before the ceiling hit, and which weren't, so a human can decide whether to finish the assessment manually or rerun rather than getting nothing.
9. No human review decision recorded	The draft simply never becomes final	It sits labeled "Awaiting review" indefinitely. Juno doesn't nag, auto-approve, or expire it into a default state. It also doesn't disappear.
