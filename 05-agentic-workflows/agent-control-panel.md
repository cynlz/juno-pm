## Autonomy level

Contract Objective: Establishes clear, non-negotiable boundaries between autonomous operations and human-gated actions to prevent unsanctioned state mutations and external messaging risks.
Permission Tier Structure: +----------------------------------------------------------------------------------------------------+
|                                    AGENCY PERMISSION MATRIX                                         |
+----------------------------------------------------------------------------------------------------+

  [TIER 1: AUTO]                    [TIER 2: AUTO]                     [TIER 3: CONFIRM]      [TIER 4: BLOCKED]
  Read Operations                  Local Drafting                     Workspace State Write   External Messaging
  * Customer Tickets (Zendesk)     * User Story Generation            * Push to Notion        * Send Slack Broadcasts
  * Strategy Docs (Notion)         * BDD Criteria Assembly            * Create Jira Issue     * Auto-Reply Zendesk
  * Eng Specs (GitHub)             * Priority Risk Scoring            * Update Backlog State  * Modify User Permissions. 
Tier 1: Read Operations (AUTO)
Threshold: Fully Autonomous.
Allowed Actions: Retrieving Zendesk customer tickets, searching Gong call transcripts, querying Notion Q3 strategy docs, and reading GitHub OpenAPI architecture specs.
Boundary: Zero side effects on external systems.
Tier 2: Draft Operations (AUTO)
Threshold: Fully Autonomous within Local Scratchpad Memory.
Allowed Actions: Synthesizing multi-channel feedback, scoring ARR risk levels, formatting BDD acceptance criteria (Given-When-Then), applying verifiability badges (🟢 Verified vs. 🟡 Unverified), and rendering interactive preview cards in private Slack threads.
Boundary: All outputs are bounded to the thread context. Zero writes to shared production databases.
Tier 3: Workspace State Mutation (CONFIRM · Human Gate)
Threshold: Human-in-the-Loop Approval Required.
Allowed Actions: Executing push_to_notion(page_id, content) and create_jira_issue(project_id, issue_data).
Boundary: Juno cannot hit the write API endpoint autonomously. Database writes are strictly locked until a PM reviews the Slack preview card and physically clicks the primary action button ([Push to Notion Draft] / [Create Draft Jira Issue]).
Tier 4: External Communication (BLOCKED)
Threshold: Permanently Disabled / Out of Scope.
Prohibited Actions: Broadcasting Slack messages to public channels, sending emails, auto-replying to Zendesk customer tickets, or altering production user permissions.
Boundary: Hard-blocked at the API harness layer.

## Controls

- **Kill switch:** LEVER 1 · Define Stop Conditions (max_steps & Termination Rules)
Configuration Parameter: max_steps = 5
Task Timeout: 15 seconds
Termination & Abort Triggers
Loop Ceiling Reached: Execution immediately halts and aborts if Juno completes 5 tool turns without reaching a complete draft state for the interactive Slack preview card.
Consecutive System Errors: Aborts the execution loop upon encountering 3 consecutive tool call errors (e.g., API timeout on the Zendesk ticket index or database connection failure).
Low Confidence & Context Conflict: Halts execution if the self-assessed model confidence drops below 70% or if retrieved RAG sources yield hard contradictions (e.g., an active Q3 OKR directly violates an engineering API rate limit spec).
Human Execution Cancel: Immediately terminates all active tool calls if the PM executes the /juno pause or /juno stop command in the active Slack thread.
Abort Action & Failure Mode
Upon aborting, Juno logs the current thread execution stack trace, releases working memory, and posts a fallback status card in the Slack thread:
⚡ Juno Execution Paused

Reason: [Max steps reached / 3 consecutive tool errors / Low confidence (< 70%)]

Action: Handing back raw retrieved context for PM review. No external workspace state was modified. <ElicitationsGroup>

- **Escalate-on-stuck:** Contract Objective: Guarantees system resilience by defining deterministic degradation pathways whenever tool calls fail, confidence drops, loop safety ceilings trigger, or human gates reject generated outputs.

Confidence Scoring Model: After RAG context ingestion and ReAct tool execution, the model evaluates its output across three dimensions: Context Grounding Rate (percentage of claims backed by citations), Constraint Alignment Score (degree of fit with engineering specs), and Ambiguity Index (clarity of raw customer signals).

High Confidence (≥85%)	Low Risk	
Generate Full Draft Card

Standard Approval Gate: PM reviews generated BDD criteria and clicks button to execute workspace state mutation.
Medium Confidence (70%−84%)	Moderate Risk

Guided PM Review: PM must review and manually verify or edit the flagged 🟡 Unverified Assumption badges before write buttons become enabled.
Low Confidence (<70%)	High Risk

System prevents drafting speculative requirements. Automatically logs reason for low confidence (e.g., missing API rate limit specs or conflicting OKR priorities).

Mandatory Escalation & Handback: Juno posts an escalation card handing back control to the PM with raw retrieved signal context attached for manual triage.
Automated Trigger Rules
Hard Friction Override: If retrieved strategy OKRs directly contradict engineering architecture constraints, confidence automatically caps at 50%, immediately triggering the Low Confidence escalation handback.
Missing Citation Penalty: Any BDD acceptance criterion lacking a direct [Source: ID] citation penalty-deducts 15% from the total confidence score, forcing the card into the Medium Confidence guided review tier.

## Permissions

Contract Objective: Enforces absolute principle-of-least-privilege across all database systems, vector stores, and external API integrations, guaranteeing that tool credentials cannot be exploited to perform unauthorized operations.
Detailed Access Control Matrix

Security & Boundary Enforcement Rules
Token Isolation: Read tools and write tools utilize separate, isolated API credentials. The read token payload completely omits write scopes at the OAuth gateway level.
Payload Sanitization: All user inputs and API responses pass through a PII/PHI filter prior to model context ingestion, redacting personal identifiable information, secret keys, and authorization headers.
Audit Trail Logging: Every tool call—whether successful, denied, or gated—is logged with a persistent execution trace ID, timestamp, calling user ID, and input parameters in the system security audit store.
